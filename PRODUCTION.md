# Production

The live site is https://dwlobby.vercel.app, on the Vercel project `gte-unofficial-dandys-world-lobby-finder` of the team `akotheakos-projects`. Its functions run in `iad1`, in the US East, next to its database, the Neon project `dandys-world-team-finder` (`little-tooth-50228811`, in the organization `org-cool-violet-32198318`). The test database of `.env.test` is the Neon project `gte-testing-2`. The `vercel` and `neonctl` CLIs reach both, after `npm i -g vercel neonctl`, `vercel login`, `vercel link` and `neonctl auth`. The Vercel dashboard is reached through the Claude in Chrome extension, in a Google Chrome that is logged in to Vercel.

The production database is only ever read, and a check never runs SQL on it.

## Limits

Every check-in takes the same database lock, so check-ins run one after another across all of the Vercel functions. That lock is the first limit that a big crowd reaches. Past it, the check-ins queue up, the page's counters and searches answer later and later, and Vercel finally ends the slowest ones with a timeout. The data stays correct, because the lock is what keeps it correct. `npm run test:load`, which `README.md` explains, measures this limit. The free plans are the second limit. Vercel Hobby and Neon's free plan each allow a fixed amount of compute per month, and the site stops answering once either runs out. Roblox is the third, because it answers 429 to an IP address that sends too many requests, and Vercel's functions share a few addresses.

Vercel Hobby emails the owner as a limit gets close and pauses the project when it is reached. The `DATABASE_URL` on Vercel uses Neon's pooled host, whose name contains `-pooler`, because every Vercel function opens connections of its own. Vercel marks the Neon variables as sensitive, so neither the CLI nor the Environment Variables page shows their values, and the `.env.local` tab of the database in Vercel's Storage tab shows them instead. Vercel Pro and Neon Launch raise the monthly limits once the crowd is real, and Vercel Hobby is only for projects without income, such as ads or donations.

## Log lines

The server logs what it needs for finding out which limit was reached. Vercel shows these lines under the project's Logs tab, for one hour on Hobby:

- `Slow check-in: ...` is a check-in that took more than a second. It tells how long the check-in waited for the lock and how long it held it, with the number of open pages and teams. A long wait means that the lock is full, and a long hold means that each check-in got slower.
- `GET /api/... failed:` and `POST /api/... failed:` are crashed requests, with their error and stack.
- `Roblox username lookup answered 429`, `Roblox profile lookup answered ...` and `Roblox badge check failed: ...` are Roblox refusing or failing a verification, and the user sees "Roblox is busy right now, try again in a minute".
- `Database connection lost: ...` is Neon dropping a connection, which the server survives.

## Checking production

A check of production goes through every step below, and the report names each step with what it found, including the steps that could not be done. A step counts as done only once its command ran. Everything that only the user can do, such as reading a dashboard or logging in again, goes into a last section of the report, titled "What you need to do", as a numbered list where each item says exactly where to click and what to report back, so that it cannot get lost among the results.

Every check writes its report to `production-reports/`, in a file named after the moment of the check, such as `production-reports/2026-10-12-1420.md`. Git ignores that folder, so the reports stay on this computer. The file holds the same report that the user gets, and never a secret, such as a connection string or a cookie secret.

1. Earlier report. The check first reads the newest file in `production-reports/`, when there is one, and the report then says what changed since that check, such as a limit that grew, a new error or a new deployment. Two reports also give each usage step a real trend.
2. Access. Every later step needs the logins. `vercel whoami` has to print `akotheakotheako-3541`, `vercel project inspect` has to name `gte-unofficial-dandys-world-lobby-finder`, which shows that the folder is still linked, and `neonctl me` has to print the user instead of asking for a login. When one of them fails, the report starts with that, and with the command that the user runs to log in again, such as `vercel login`, `vercel link` or `neonctl auth`, since only the user can complete a login in the browser.
3. Deployed code. `vercel ls --prod` lists the production deployments, and the newest one has to be "Ready". `git status -sb` shows whether the local `main` is ahead of `origin/main`, which means that commits are not pushed, so production does not run them. `git log origin/main -1 --format="%h %cd %s"` gives the newest pushed commit. `vercel inspect` on the newest deployment shows no commit, so the check compares times instead: the newest deployment was built from the newest pushed commit when `vercel inspect` gives it a `created` time after that commit's time.
4. Environment variables. `vercel env ls production` lists the names of the variables, and `DATABASE_URL` and `COOKIE_SECRET` both have to be among them. A missing one breaks the API, while the page and `/api/images/toons` of the next step can still answer 200.
5. The site answers. `curl -s -o /dev/null -w "%{http_code}" https://dwlobby.vercel.app` and the same for `https://dwlobby.vercel.app/api/images/toons` both have to print 200. The second one runs the server function without touching the database. A check never posts to `/api/check-in`, since that writes a fake page into the real database.
6. Errors and slowness. This step only sees the last hour, since that is all that Vercel Hobby keeps. Each line of "Log lines" gets its own search by name, with `vercel logs --environment production --since 1h --query "<text>"`, for the texts `Slow check-in`, `failed:`, `Roblox username lookup answered`, `Roblox profile lookup answered`, `Roblox badge check failed` and `Database connection lost`. A search by `--level error` would miss `Slow check-in`, which the server writes as an ordinary log line. Waits of several seconds for the lock in the slow check-ins mean that the site has more check-ins than the lock lets through. `vercel logs --environment production --since 1h --status-code 5xx` lists every failed answer.
7. Traffic. `vercel logs --environment production --since 1h --limit 1000 --json` prints one JSON line per request, and counting the lines by `requestMethod`, `requestPath` and `responseStatusCode` gives the traffic of the last hour. The number of `POST /api/check-in` requests, divided by 3600, is the check-ins per second, and the report gives both numbers side by side with the limit that `README.md` measured, such as "0.2 check-ins per second against about 13". A count of exactly 1000 means that the limit cut the list, and a smaller `--since` gives the true rate.
8. Database state. `neonctl branches list --project-id little-tooth-50228811 --output json` has to show the `main` branch with the `current_state` "ready", and `neonctl operations list --project-id little-tooth-50228811 --output json` lists the latest starts and suspensions of its compute, where every `failures_count` has to be 0. Both commands only read the project's settings, so they work in an hour without any check-ins. Answered `POST /api/check-in` requests in the traffic also show that the database works, since every check-in reads and writes it.
9. Database usage. `neonctl projects get little-tooth-50228811 --org-id org-cool-violet-32198318 --output json` reads the project's details without touching its data. `compute_time_seconds` divided by 3600 is the compute-hours used since `consumption_period_start`, `data_transfer_bytes` is the data sent, and the database is capped at `branch_logical_size_limit_bytes`. The free plan's monthly allowances, to compare these with, come from https://neon.com/pricing, read during the check, since remembered numbers go out of date. When the page cannot be read, the report says that the allowance is unconfirmed. Each amount that renews every month also gets a projection to the end of the period, which is the amount used, divided by the days since `consumption_period_start`, times the days of the whole period.
10. Vercel usage. Only the dashboard shows it, because Hobby refuses `vercel usage` and `vercel metrics`. Claude in Chrome opens https://vercel.com/akotheakos-projects/~/usage in a new tab of the user's Chrome, where the user is logged in to Vercel, reads the page's text and closes the tab again. The report gives each limit's use, especially the ones about functions and data transfer. When the extension is not connected, "What you need to do" asks the user to open that page and report those numbers instead. The Hobby allowances come from https://vercel.com/pricing, read during the check, like Neon's. Each limit gets a projection to the end of the period that the page shows, the same way as Neon's.
11. Risks. The report ends with what could break next, such as a limit that is more than half used or projected to pass half by the end of its period, unpushed commits, slow check-ins in the logs, or check-ins per second close to the measured limit. It also says that the logs only covered the last hour, so a problem from earlier would not have shown.
